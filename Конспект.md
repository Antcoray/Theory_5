### Теория

#### База данных и СУБД

**База данных (БД)** — совокупность данных, организованных в соответствии с концептуальной структурой, описывающей характеристики данных и взаимоотношения между ними, поддерживающая одну или более областей применения (ISO/IEC 2382-1:1993).

**СУБД (система управления базами данных)** — совокупность программных и лингвистических средств, обеспечивающих управление созданием и использованием БД (ISO/IEC TR 10032:2003).

*Где пригодится: ЛР1 — эти определения нужны в разделе «теоретические знания по теме лабораторной»; на защите могут спросить формально.*

Требования к СУБД: установление многосторонних связей, производительность, минимальные затраты, минимальная избыточность, возможности поиска, целостность, безопасность и секретность, связь с прошлым/будущим, настройка, перемещение данных, простота.

Основные функции СУБД: управление данными во внешней памяти; управление буферами оперативной памяти; управление транзакциями; журнализация изменений, резервное копирование и восстановление после сбоев; поддержка языков БД (DDL — язык определения данных, DML — язык манипулирования данными).

Типовая организация СУБД: ядро СУБД (менеджер данных, менеджер буферов, менеджер транзакций, менеджер журнала), компилятор языка БД, подсистема поддержки времени выполнения, набор сервисных утилит.

#### Классификация баз данных

| Критерий | Виды |
|---|---|
| По степени структуризации | неструктурированные, частично структурированные, структурированные |
| По характеру данных | фактографические, лексикографические |
| По распределённости | централизованные, распределённые |
| По количеству пользователей | однопользовательские, многопользовательские |
| По способу доступа | файл-серверные, клиент-серверные, встраиваемые |
| По модели данных | иерархические, сетевые, **реляционные**, объектно-реляционные, объектно-ориентированные, многомерные |

*Где пригодится: ЛР1 — при обосновании выбора «реляционная СУБД» в теоретической части.*

#### Реляционная модель данных

Предложена сотрудником IBM Эдгаром Коддом в 1969–1970 гг. Компоненты модели (К. Дейт): структурный аспект, аспект целостности, аспект манипулирования.

| Элемент реляционной модели | Форма представления |
|---|---|
| Отношение | Таблица |
| Схема отношения | Строка заголовков столбцов (заголовок таблицы) |
| Кортеж | Строка таблицы |
| Сущность | Описание свойств объекта |
| Атрибут | Заголовок столбца |
| Домен | Множество допустимых значений атрибута |
| Значение атрибута | Значение поля в записи |
| Первичный ключ | Один или несколько атрибутов, однозначно определяющих кортеж |
| Тип данных | Тип значений элементов таблицы |

Основные свойства отношения: нет двух одинаковых кортежей; порядок кортежей не определён; порядок атрибутов не определён; значения всех атрибутов атомарны.

Требования к таблицам реляционной БД: все строки уникальны (нет строк с одинаковым PK — Primary Key, первичный ключ; подробнее см. ниже раздел «Ключи»); имена столбцов различны, значения простые (нет группы значений в одной ячейке); все строки одной таблицы имеют одну структуру; порядок строк произволен.

*Где пригодится: ЛР1 — при описании сущностей и их атрибутов; ЛР2 — атомарность значений это ключевое условие 1НФ.*

#### Ключи

- **Первичный ключ (PK)** — атрибут(ы), однозначно идентифицирующие каждый кортеж.
- **Возможный (потенциальный) ключ** — любая комбинация атрибутов, однозначно определяющая кортежи.
- Ключ **не избыточен**, если состоит из минимально необходимого набора атрибутов.
- **Внешний ключ (FK)** — неключевой атрибут A отношения R1, значения которого являются значениями ключевого атрибута B отношения R2.

Причины использования ключей: исключение дублирования значений, упорядочение кортежей, ускорение работы с кортежами, организация связывания таблиц.

*Где пригодится: ЛР1 — описание PK/FK каждой сущности; ЛР3 — реализация через `PRIMARY KEY`/`FOREIGN KEY` при создании таблиц.*

#### Виды связей и целостность

| Характеристика полей связи | 1:1 | 1:М | М:1 | М:М |
|---|---|---|---|---|
| Поля связи основной таблицы | ключ | ключ | не ключ | не ключ |
| Поля связи дополнительной таблицы | ключ | не ключ | ключ | не ключ |

Контроль целостности связей: каждой записи основной таблицы соответствует ноль или более записей дополнительной; в дополнительной таблице нет «сиротских» записей без родителя в основной; каждая запись дополнительной таблицы имеет только одну родительскую запись. Проверки целостности выполняются при добавлении записи в дополнительную таблицу, при изменении записи в основной/дополнительной таблице, при удалении записи из основной таблицы.

*Где пригодится: ЛР1 — обязательное требование AC — представить в схеме **все три** вида связи (1:1, 1:М, М:М). Для М:М в реляционной модели всегда нужна промежуточная (связующая) таблица.*

#### Реляционная алгебра

Реляционная алгебра — замкнутая система операций над отношениями.

| Операция | Смысл |
|---|---|
| Объединение (UNION) | кортежи, принадлежащие A, B или обоим (совместимые по типу отношения) |
| Пересечение (INTERSECT) | кортежи, принадлежащие одновременно A и B |
| Разность (MINUS) | кортежи из A, не принадлежащие B |
| Произведение (декартово) | все сочетания кортежей A и B (конкатенация) |
| Ограничение (Selection, `WHERE`) | подмножество строк по условию |
| Проекция (Projection, список столбцов в `SELECT`) | подмножество столбцов |
| Соединение (Join) | декартово произведение + выборка по совпадающим атрибутам |
| Деление (Division) | обратная операция к произведению |
| Переименование (Rename) | смена имени атрибута |
| Расширение (Extend) | добавление вычисляемого атрибута |
| Подведение итогов (Summarize) | «вертикальные»/групповые вычисления |

*Где пригодится: это теоретическая база операторов SQL — объединение/пересечение/разность → `UNION`/`INTERSECT`/`MINUS` (ЛР4), соединение → все виды `JOIN` (ЛР4), проекция/ограничение → `SELECT`/`WHERE` (ЛР3).*

#### Инфологическое проектирование

**Инфологическое (концептуальное) описание** — верхний уровень абстракции: описание объектов предметной области, их атрибутов и связей между ними, без привязки к конкретной СУБД.

Отличается от:
- **Даталогического** проектирования — описание логической структуры средствами конкретной СУБД (таблицы, связи, атрибуты) → тема **ЛР2**.
- **Физического** проектирования — размещение данных на носителе (организация данных, управление свободной памятью, сжатие) → тема **ЛР3**.

Цели проектирования БД: хранение всех необходимых данных; получение данных по всем нужным запросам; сокращение избыточности/дублирования; обеспечение целостности; сокращение времени доступа.

Подходы к проектированию: (1) сбор информации в одну таблицу с последующей декомпозицией через нормализацию; (2) формулирование знаний о системе и получение схемы через CASE-средства; (3) структурирование информации в рамках системного анализа.

*Где пригодится: ЛР1 — именно инфологическую (не нормализованную) модель нужно нарисовать в этой лабе; нормализация — уже следующий шаг (ЛР2).*

#### Практический алгоритм для ЛР1

1. Выбрать предметную область (тема проекта).
2. Выписать обязательные сущности: `users` (пользователи), `roles`/`user_roles` (роли, включая связь M:M пользователь-роль), `audit_log`/`action_log` (журнал действий) — это закрывает обязательные функциональные требования AC п.2.
3. Добавить предметные сущности так, чтобы их было ≥10 в сумме, и чтобы явно присутствовали все три вида связей. Например: `1:1` — `users` ↔ `user_profiles`; `1:M` — `orders` → `order_items`; `M:M` — `products` ↔ `categories` через `product_categories`.
4. На схеме (draw.io/Miro/…) отрисовать сущности прямоугольниками с полным списком атрибутов внутри (без вынесения в отдельную таблицу нормализации — это ещё «сырая», не нормализованная модель), связи — линиями с указанием мощности (1, М).
5. Для каждой сущности отдельно описать (текстом или таблицей): имя поля → тип данных → ограничения (NOT NULL/UNIQUE/PK/FK) → с какой сущностью связано.

## Лабораторная работа №2 — Даталогическая модель, нормализация (3НФ)

### Условие
1. Разработать даталогическую модель утверждённой в ЛР1 БД.
2. Привести БД к третьей нормальной форме (в случае необходимости денормализации — быть готовым обосновать).

### Acceptance Criteria
1. Разработана даталогическая модель БД.
2. Выполнен п.2 условия (приведение к 3НФ).
3. Готовность привести БД к последующим нормальным формам (Бойса-Кодда, 4НФ, 5НФ, 6НФ).
4. Теоретические знания по теме лабораторной.

### Теория

#### Даталогическое проектирование

Описание логической структуры данных средствами конкретной СУБД: описание таблиц, описание связей между таблицами, описание атрибутов. Именно на этом этапе не нормализованная инфологическая модель ЛР1 превращается в набор конкретных таблиц с типами колонок и ключами — но ещё **до** физического создания в БД (это уже ЛР3).

*Где пригодится: ЛР2 — это первый пункт условия; отличие от ЛР1 в том, что здесь уже фиксируется конкретная структура таблиц (а не абстрактные сущности).*

#### Аномалии не нормализованных отношений

Избыточное дублирование данных (пример: телефон сотрудника дублируется в каждой строке при повторении отдела) порождает три вида аномалий:
- **Аномалии добавления** — нельзя добавить факт (например, номер комнаты), пока нет связанной записи.
- **Аномалии удаления** — при удалении одной строки теряется и другая независимая информация.
- **Аномалии модификации** — изменение значения требует правки сразу нескольких строк (риск рассогласования).

*Где пригодится: ЛР2 — это и есть обоснование, зачем вообще нужна нормализация; полезно упомянуть в защите.*

#### Нормальные формы

**1НФ.** Отношение находится в первой нормальной форме тогда и только тогда, когда каждый кортеж содержит только одно (атомарное) значение для каждого атрибута.

Условия 1НФ: нет одинаковых кортежей; кортежи и атрибуты не упорядочены (различаются по имени); все значения атрибутов атомарны.

Приведение к 1НФ: устранить повторяющиеся кортежи; создать отдельное отношение для каждого набора связанных данных; идентифицировать каждый кортеж первичным ключом.

```
До 1НФ:  Сотрудник | Проекты (список через запятую)
После:   Сотрудник | Проект   (одна строка = одна пара сотрудник-проект)
```

**2НФ.** Отношение в 2НФ ⇔ отношение в 1НФ **и** нет неключевых атрибутов, зависящих от **части** составного ключа (устранение частичной функциональной зависимости).

Приведение к 2НФ: вынести в отдельную таблицу значения, зависящие только от части ключа, связать через FK.

**3НФ.** Отношение в 3НФ ⇔ отношение в 2НФ **и** все неключевые атрибуты взаимно независимы (нет транзитивной зависимости неключевого атрибута от другого неключевого через PK).

Приведение к 3НФ: удалить поля, не зависящие напрямую от ключа (транзитивно зависимые выносятся в отдельную таблицу).

```
2НФ:  Отдел | Адрес | Телефон      (Телефон зависит от Адреса, а не от Отдела напрямую)
3НФ:  Отдел | Адрес   и   Адрес | Телефон
```

| Критерий | Слабо нормализованные (1НФ/2НФ) | Сильно нормализованные (3НФ) |
|---|---|---|
| Адекватность предметной области | хуже | лучше |
| Лёгкость разработки/сопровождения | сложнее | легче |
| Скорость INSERT/UPDATE/DELETE | медленнее | быстрее |
| Скорость SELECT (выборки) | быстрее | медленнее (нужны JOIN) |

*Где пригодится: ЛР2 — прямое требование AC привести к 3НФ; на защите могут попросить построить цепочку 1НФ→2НФ→3НФ на вашем примере. Последняя строка таблицы — готовый аргумент «за» умеренную денормализацию, если её потребуется обосновать (AC допускает это явно).*

**НФБК (нормальная форма Бойса-Кодда).** Отношение в НФБК ⇔ отношение в 3НФ и в отношении есть только один потенциальный (возможный) ключ, к которому всё зависит. Метод приведения: вынести в отдельную таблицу потенциальные первичные ключи.

**4НФ.** Отношение в 4НФ ⇔ отношение в НФБК и не содержит нетривиальных **многозначных** зависимостей (когда один атрибут порождает несколько независимых наборов значений другого — пример: абитуриент связан одновременно с несколькими факультетами и несколькими предметами независимо друг от друга). Решение — разбить на две таблицы по каждой независимой связи.

**5НФ и 6НФ** упоминаются в лекциях только по названию (разложение без потерь на произвольное число проекций для 5НФ; учёт временных/исторических изменений для 6НФ) — на курсе от студента требуется только **готовность обсуждать** идею (AC п.3), детальные примеры для лабы не нужны.

Требования к нормализации (итоговый чек-лист): минимальность PK; минимальная избыточность; без потери производительности; непротиворечивость данных при DML; гибкость схемы к расширению; стабильное время отклика на разные запросы; актуальность данных.

*Где пригодится: ЛР2 — быть готовым объяснить, почему БД не приведена к 4НФ/5НФ/6НФ (в реальных проектах чаще всего останавливаются на 3НФ/НФБК из соображений производительности — это и есть законное обоснование денормализации из AC п.2a.*

### Теория

#### Физическое проектирование

Описание физической структуры БД — её размещения на запоминающем устройстве: способы организации данных, управления свободной памятью, сжатия данных.

#### Основные объекты БД Oracle

| Объект | Описание |
|---|---|
| Таблица (Table) | базовый модуль хранения, состоит из столбцов |
| Представление (View) | логическое представление данных из одной/нескольких таблиц |
| Последовательность (Sequence) | генерация числовых значений (суррогатные ключи) |
| Индекс (Index) | ускорение отдельных запросов |
| Синоним (Synonym) | альтернативное имя объекта |

Правила именования таблиц/столбцов: начинаются с буквы; 1–30 символов; допустимы `A-Z a-z 0-9 _ $ #`; не дублируют имена других объектов пользователя и зарезервированные слова.

#### Типы данных Oracle

| Тип | Описание |
|---|---|
| `VARCHAR2(n)` | строка переменной длины, до 4000 байт (до 2000 в старых версиях) |
| `CHAR(n)` | строка фиксированной длины, до 2000 байт |
| `NUMBER(p,s)` | число: `p` — точность (кол-во значащих цифр), `s` — масштаб (кол-во знаков после запятой) |
| `DATE` | дата+время (с точностью до секунды) |
| `TIMESTAMP[(precision)]` | дата+время с долями секунды |
| `INTERVAL YEAR TO MONTH` / `INTERVAL DAY TO SECOND` | интервалы времени |
| `BLOB`, `CLOB`, `NCLOB` | большие бинарные/символьные объекты (внутренние LOB — Large Object, «большой объект»: тип данных для хранения больших массивов информации, которые не помещаются в обычные текстовые/числовые колонки) |
| `BFILE` | указатель на внешний файл (внешний LOB) |

Пример поведения `NUMBER`:

| Входное значение | Тип столбца | Хранится |
|---|---|---|
| 7456123.89 | `NUMBER(9,2)` | 7456123.89 |
| 7456123.89 | `NUMBER(9)` | 7456123 |
| 7456123.89 | `NUMBER(6)` | ошибка: превышена точность |

*Где пригодится: ЛР3 — выбор правильного типа колонки при `CREATE TABLE`; ошибка `NUMBER(6)` — частый повод для «наложения ограничений» на этапе создания.*

#### Создание, изменение, удаление таблиц

```sql
CREATE TABLE tab1 (
    id          NUMBER(6)     CONSTRAINT tab1_id_pk PRIMARY KEY,
    first_name  VARCHAR2(32),
    last_name   VARCHAR2(32)  CONSTRAINT tab1_lname_nn NOT NULL,
    email       VARCHAR2(50)  CONSTRAINT tab1_email_nn NOT NULL
                              CONSTRAINT tab1_email_uk UNIQUE,
    create_date DATE          DEFAULT SYSDATE,
    salary      NUMBER(8,2)   CONSTRAINT tab1_salary_ck_min CHECK (salary > 0)

```

Ограничение можно задавать на уровне столбца (как выше) или на уровне таблицы:

```sql
CREATE TABLE tab1 (
    id   NUMBER,
    name VARCHAR2(32),

```

Изменение структуры:

```sql
ALTER TABLE tab1 ADD (phone VARCHAR2(20));
```

#### Ограничения (constraints)

| Ограничение | Смысл |
|---|---|
| `NOT NULL` | запрет пустого значения |
| `UNIQUE` | запрет дублирующихся значений |
| `PRIMARY KEY` | уникальность + `NOT NULL`, один PK на таблицу |
| `FOREIGN KEY` | ссылочная целостность на другую таблицу |
| `CHECK` | произвольное логическое условие на значение столбца |

```sql
CONSTRAINT fk_deptno FOREIGN KEY (department_id)
    REFERENCES departments (department_id) ON DELETE CASCADE;
-- ON DELETE CASCADE  — при удалении родителя удаляются дочерние строки
-- ON DELETE SET NULL — при удалении родителя FK в дочерних строках становится NULL
```

`CHECK` не может: содержать подзапросы, вызывать `SYSDATE`/`USER`/`UID`/`USERENV` и т.п. недетерминированные функции, вызывать пользовательские функции, ссылаться на псевдостолбцы или объекты вне своей таблицы.

*Где пригодится: ЛР3 — прямое требование AC 1c («проставлены… констрейнты»); ЛР5 — альтернатива `CHECK` для простых правил vs. триггер для более сложной логики.*

#### Индексы

Создаются автоматически (для PK/UNIQUE), вручную (`CREATE INDEX`) или поддерживаются автоматически.

```sql
CREATE INDEX idx_emp_lastname ON employees(last_name);
```

Когда создавать индекс: колонка используется в `WHERE`/`JOIN`; запрос выбирает малую долю строк (обычно < 4% значений); в колонке немного `NULL`. Когда **не** стоит: таблица часто обновляется; в таблице мало строк.

Индексы бывают по одной/нескольким колонкам, уникальные/неуникальные, партиционированные/непартиционированные, основанные на функциях.

| B-Tree | Bitmap |
|---|---|
| Много разных значений (высокая селективность) | Мало различных значений (низкая селективность) |
| Обновление лёгкое | Обновление крайне тяжёлое |
| Неэффективен для `OR` | Эффективен для `OR` |
| Используется в OLTP | Используется в DataWarehouse |

**B-Tree** (сбалансированное дерево) — структура индекса по умолчанию в Oracle: хранит указатели на строки в виде дерева, отсортированного по значению колонки, что даёт быстрый поиск как по точному значению, так и по диапазону. **Bitmap**-индекс вместо дерева хранит для каждого возможного значения битовую карту (последовательность 0/1 — есть ли значение в строке), поэтому эффективен только при небольшом числе различных значений. **OLTP** (Online Transaction Processing — оперативная обработка транзакций) — режим работы БД с большим числом коротких операций чтения/записи (типичное «боевое» бизнес-приложение); **DataWarehouse** (хранилище данных) — БД, оптимизированная под редкие, но тяжёлые аналитические запросы по большим объёмам исторических данных (аналог термина **OLAP**, Online Analytical Processing).

```sql
ALTER INDEX idx_emp_lastname REBUILD [ONLINE];    -- перестройка
ALTER INDEX idx_emp_lastname COALESCE;            -- дефрагментация без блокировки (блокировка — временный запрет другим сеансам изменять/читать данные, пока с ними работает текущая операция, нужен для целостности при параллельном доступе)
ANALYZE INDEX idx_emp_lastname VALIDATE STRUCTURE;-- проверка целостности
DROP INDEX idx_emp_lastname;
```

*Где пригодится: ЛР3 — AC явно требует «проставлены индексы» уже на этапе физической модели (не путать с ЛР4, где индексы понадобятся ещё и для объяснения `EXPLAIN PLAN`).*

#### DML: вставка, изменение, удаление данных


#### Простая выборка данных (SELECT)


Операторы сравнения: `=`, `<>`/`!=`, `<`, `>`, `<=`, `>=`, а также `ANY`/`ALL` для сравнения со множеством значений подзапроса.

Логические операторы: `NOT`, `AND`, `OR`.

Специальные операторы фильтрации:

| Оператор | Смысл | Пример |
|---|---|---|
| `LIKE` | соответствие шаблону (`_` — один символ, `%` — любое число символов) | `WHERE color LIKE '_l%'` |
| `IN` | вхождение в список | `WHERE id IN (1,2,4)` |

Полезные функции для простых выборок:

```sql

SELECT CONCAT('Hello ', 'world') FROM DUAL;          -- или: 'Hello' || ' ' || 'world'
SELECT UPPER(name), LOWER(name), INITCAP(name), LENGTH(name), SUBSTR(name,1,3) FROM tab1;
SELECT column1, column1/(column1+column2)*100 AS perc FROM tab1;  -- вычисляемое поле + псевдоним

```

**Транзакция** — последовательность операций с БД, которая должна выполниться целиком или не выполниться вовсе (например, перевод денег = списание у одного + зачисление другому). **Транзакции** (нужны для того, чтобы объяснить `COMMIT`/`ROLLBACK` при заполнении тестовыми данными): свойства ACID (Atomicity, Consistency, Isolation, Durability) — атомарность (выполняется целиком или откатывается), согласованность (БД переходит из одного корректного состояния в другое), изолированность (параллельные транзакции не видят промежуточных изменений друг друга), долговечность (после `COMMIT` изменения сохраняются даже при сбое). Управление: `COMMIT`, `ROLLBACK`, `SAVEPOINT`, `ROLLBACK TO SAVEPOINT`.

Проблемы параллельной работы (возникают, когда несколько транзакций одновременно работают с одними данными) и уровни изоляции:

| Уровень изоляции | Фантомные чтения | Неповторяющиеся чтения | Грязные чтения |
|---|---|---|---|
| READ UNCOMMITTED | разрешены | разрешены | разрешены |
| READ COMMITTED | разрешены | разрешены | запрещены |
| REPEATABLE READ | разрешены | запрещены | запрещены |
| SERIALIZABLE | запрещены | запрещены | запрещены |

Пояснение проблем из таблицы: **грязное чтение** (dirty read) — транзакция читает ещё не зафиксированные (`COMMIT`) изменения другой транзакции, которые могут потом откатиться; **неповторяющееся чтение** (non-repeatable read) — повторное чтение той же строки в рамках одной транзакции даёт другой результат, т.к. её успела изменить и зафиксировать другая транзакция; **фантомное чтение** (phantom read) — повторный запрос с тем же условием возвращает другой набор строк, т.к. другая транзакция успела вставить/удалить подходящие строки.

*Где пригодится: ЛР3 — AC явно требует «готовность пояснить смысл всех операторов»; транзакции и `COMMIT` нужны сразу после первых `INSERT`. ЛР5 — понимание транзакций необходимо для автономных транзакций в триггерах.*

### Теория

#### JOIN — соединение таблиц

Соединение — декартово произведение + фильтрация по условию совпадения атрибутов (реляционная алгебра, см. ЛР1).

| Вид JOIN | Синтаксис | Что возвращает |
|---|---|---|
| NATURAL JOIN | `FROM a NATURAL JOIN b` | по всем одинаково названным столбцам (неявно) |
| JOIN … USING | `FROM a JOIN b USING (id)` | явное соединение по одному общему столбцу |
| JOIN … ON | `FROM a JOIN b ON (a.id = b.id)` | явное соединение по любому условию |
| INNER JOIN | `FROM a JOIN b ON (...)` (по умолчанию) | только совпавшие строки из обеих таблиц |
| LEFT OUTER JOIN | `FROM a LEFT JOIN b ON (...)` | все строки `a` + совпавшие из `b` (иначе `NULL`) |
| RIGHT OUTER JOIN | `FROM a RIGHT JOIN b ON (...)` | все строки `b` + совпавшие из `a` |
| FULL OUTER JOIN | `FROM a FULL JOIN b ON (...)` | все строки обеих таблиц, несовпавшие поля — `NULL` |
| CROSS JOIN | `FROM a CROSS JOIN b` | декартово произведение (все со всеми) |
| SELF JOIN | `FROM emp e1 JOIN emp e2 ON (...)` | таблица соединяется сама с собой (напр. сотрудник-начальник) |

```sql
-- INNER (по умолчанию через WHERE — устаревший, но встречается синтаксис)
SELECT * FROM departments d, locations l WHERE d.location_id = l.location_id;

-- SELF JOIN: сотрудник и его начальник в одной таблице employees
SELECT e1.last_name AS employee, e2.last_name AS manager
FROM   employees e1
JOIN   employees e2 ON (e1.manager_id = e2.employee_id);

-- LEFT OUTER JOIN: все сотрудники, даже без отдела
SELECT e.last_name, e.job_id, d.department_name
FROM   employees e
LEFT OUTER JOIN departments d ON (e.department_id = d.department_id);

-- FULL OUTER JOIN
SELECT e.last_name, d.department_name
FROM   employees e
FULL OUTER JOIN departments d ON (e.department_id = d.department_id);

-- CROSS JOIN: декартово произведение
SELECT e.last_name, d.department_name
FROM   employees e CROSS JOIN departments d;
```

*Где пригодится: ЛР4 — это прямое требование AC п.2a; на защите нужно уметь написать любой из этих JOIN «с нуля» под свои таблицы (AC п.6).*

#### Множественные операции над результатами запросов

```sql
SELECT employee_id, job_id FROM employees
UNION                                   -- объединение без дублей (сортирует и убирает повторы)
SELECT employee_id, job_id FROM job_history;

SELECT employee_id, job_id FROM employees
UNION ALL                               -- объединение с дублями (быстрее, без сортировки)
SELECT employee_id, job_id FROM job_history;

SELECT employee_id, job_id FROM employees
INTERSECT                               -- только общие строки
SELECT employee_id, job_id FROM job_history;

SELECT employee_id, job_id FROM employees
MINUS                                   -- строки первого запроса, отсутствующие во втором
SELECT employee_id, job_id FROM job_history;
```

Условие для `UNION`/`INTERSECT`/`MINUS`: одинаковое число столбцов и совместимые типы в обоих запросах.

*Где пригодится: ЛР4 — AC п.3d прямо требует `UNION`.*

#### GROUP BY, HAVING, агрегатные функции

```sql
SELECT department_id, COUNT(employee_id), SUM(salary), AVG(salary), MAX(salary), MIN(salary)
FROM   employees
GROUP BY department_id
HAVING AVG(salary) > 5000;             -- фильтр НА группы (WHERE фильтрует строки ДО группировки)
```

Порядок логического выполнения запроса (важно понимать для объяснения на защите): `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY`.

Расширенная группировка:

```sql
SELECT department_id, job_id, SUM(salary) FROM employees GROUP BY ROLLUP(department_id, job_id);
-- ROLLUP добавляет промежуточные и общий итог (иерархические подытоги)

SELECT department_id, job_id, SUM(salary) FROM employees GROUP BY CUBE(department_id, job_id);
-- CUBE считает итоги по ВСЕМ комбинациям измерений

SELECT department_id, job_id, SUM(salary)
FROM   employees GROUP BY GROUPING SETS (department_id, job_id);
-- GROUPING SETS — явно заданный набор группировок (без лишних комбинаций CUBE)

SELECT DECODE(GROUPING(department_id), 1, 'Итого', department_id) dep_id, SUM(salary)
FROM   employees GROUP BY ROLLUP(department_id);
-- GROUPING(col) = 1 в строке итога по этому столбцу — удобно подписывать "Итого"
```

*Где пригодится: ЛР4 — AC п.3a/3c; `ROLLUP`/`CUBE`/`GROUPING SETS` не входят в обязательный список AC, но это стандартный набор Oracle для отчётов "с итогами" — полезно показать как "прочую сложную выборку" (AC п.1c).*

#### Оконные функции: PARTITION BY, PARTITION OVER

Оконная функция считается «по окну» строк, но **не схлопывает** их в одну строку (в отличие от `GROUP BY`).

```sql
-- ранжирование внутри всего набора
SELECT product_type, SUM(amount) total,
       RANK()       OVER (ORDER BY SUM(amount) DESC) rnk,
       DENSE_RANK() OVER (ORDER BY SUM(amount) DESC) dense_rnk
FROM   sales GROUP BY product_type;

-- нумерация строк внутри каждой партиции (PARTITION BY = "GROUP BY для окна")
SELECT ROW_NUMBER() OVER (PARTITION BY department_id ORDER BY last_name) rn,
       last_name, department_id
FROM   employees;

-- сравнение с предыдущей/следующей строкой
SELECT res_year, AVG(amount) avg_amt,
       LAG(AVG(amount), 1)  OVER (ORDER BY res_year) prev_year,
       LEAD(AVG(amount), 1) OVER (ORDER BY res_year) next_year
FROM   sales GROUP BY res_year;

-- накопительная сумма ("скользящее окно")
SELECT ename, deptno, hiredate, sal,
       SUM(sal) OVER (PARTITION BY deptno ORDER BY hiredate
                       ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) running_total,
       AVG(sal) OVER (ORDER BY hiredate
                       ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) moving_avg_3
FROM   emp;

-- доля от суммы по партиции
SELECT last_name, SUM(salary),
       RATIO_TO_REPORT(SUM(salary)) OVER (PARTITION BY department_id) share
FROM   employees WHERE department_id = 90 GROUP BY last_name, department_id;
```

Общий синтаксис скользящего окна:
`{ROWS|RANGE} BETWEEN {UNBOUNDED PRECEDING|CURRENT ROW|n PRECEDING/FOLLOWING} AND {UNBOUNDED FOLLOWING|CURRENT ROW|n PRECEDING/FOLLOWING}`.

*Где пригодится: ЛР4 — AC п.3b дословно требует `PARTITION`, `PARTITION OVER` + оконные функции; типовой пример для защиты — "top-N товаров по продажам в каждой категории" через `ROW_NUMBER() OVER (PARTITION BY category ...)`.*

#### Подзапросы (вложенные конструкции — AC п.1b)

| Тип | Где может находиться | Пример |
|---|---|---|
| Однострочный | `WHERE`, `HAVING`, `SELECT`, `ORDER BY` | `WHERE boss_id = (SELECT employee_id FROM employees WHERE last_name = 'Brown')` |
| Многострочный (`IN`) | `WHERE` | `WHERE boss_id IN (SELECT employee_id FROM employees WHERE last_name = 'Brown')` |
| Многострочный (`ANY`/`ALL`) | `HAVING`, `WHERE` | `HAVING AVG(price) > ANY (SELECT AVG(price) FROM products GROUP BY product_type)` |
| Многостолбцовый | `WHERE` | `WHERE (type_id, price) IN (SELECT type_id, MIN(price) FROM products GROUP BY type_id)` |
| Коррелированный (ссылается на внешний запрос) | `WHERE` | `WHERE price > (SELECT AVG(price) FROM products p2 WHERE p1.type_id = p2.type_id)` |
| В `FROM` (inline view) | `FROM` | `FROM subjects, (SELECT ... FROM prepods WHERE age > 70) old_school` |

Уровень вложенности подзапросов — до 255. Подзапросы также применимы в `UPDATE`, `DELETE`, `INSERT` (см. `INSERT INTO SELECT` ниже).

*Где пригодится: ЛР4 — AC п.1b «запросы с вложенными конструкциями»; коррелированные подзапросы — классика для «выбрать товары дороже средней цены в своей категории».*

#### EXISTS

```sql
SELECT p.last_name, p.first_name
FROM   prepods p
WHERE  EXISTS (SELECT 1 FROM subjects s
               WHERE p.id = s.prepod_id AND s.weekday = 'Saturday');
```

`EXISTS` проверяет только **факт наличия** строк у подзапроса (быстрее, чем `IN`, на больших наборах, т.к. не нужно материализовать список значений — достаточно найти первую подходящую строку). `NOT EXISTS` — классический способ найти «сущности без связанных записей» (например, клиентов без заказов).

*Где пригодится: ЛР4 — AC п.4a.*

```sql

```

Массовое копирование/перенос данных между таблицами без выгрузки на клиент. Также применяется для генерации тестовых данных (см. ЛР3).

*Где пригодится: ЛР4 — AC п.4b.*

#### EXPLAIN PLAN — план выполнения запроса

```sql
EXPLAIN PLAN FOR
SELECT * FROM persons WHERE last_name LIKE 'Иванов%' AND created_date < SYSDATE - 30;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
```

Пример результата и как его читать:

```
---------------------------------------------------------------------------
| Id | Operation         | Name    | Rows | Bytes | Cost (%CPU) | Time     |
---------------------------------------------------------------------------
|  0 | SELECT STATEMENT  |         |    1 |    37 |   3   (0)   | 00:00:01 |
| *1 | TABLE ACCESS FULL | PERSONS |    1 |    37 |   3   (0)   | 00:00:01 |
---------------------------------------------------------------------------
Predicate Information (identified by operation id):
   1 - filter("LAST_NAME" LIKE 'Иванов%' AND "CREATED_DATE">SYSDATE-30)
```

Основные типы шагов плана и что они означают:

| Операция | Смысл |
|---|---|
| `TABLE ACCESS FULL` | полное сканирование таблицы (медленно на больших таблицах — сигнал «не хватает индекса») |
| `TABLE ACCESS BY INDEX ROWID` | точечное чтение строк по индексу |
| `INDEX RANGE SCAN` | использован индекс для диапазонной выборки |
| `HASH JOIN` | соединение через построение хэш-таблицы (эффективно для больших наборов без подходящего индекса) |
| `NESTED LOOPS` | для каждой строки внешней таблицы — поиск во внутренней (эффективно, если внешний набор мал и есть индекс на внутренней) |
| `SORT MERGE JOIN` | оба источника сортируются по ключу соединения, затем сливаются |

Как получить план выполнения (порядок обработки запроса «под капотом»): лексический анализ → логическая оптимизация → определение возможных планов → выбор оптимального (по правилам `RULE BASED` или по стоимости `COST BASED`, современный Oracle использует **CBO** — Cost-Based Optimizer, оптимизатор, который выбирает план по расчётной «стоимости» выполнения на основе статистики) → подстановка параметров → выполнение.

Зачем нужна статистика для оптимизатора:

```sql
EXEC DBMS_STATS.GATHER_TABLE_STATS(ownname => 'HR', tabname => 'EMPLOYEES');
EXEC DBMS_STATS.GATHER_SCHEMA_STATS(ownname => 'HR');
```

Без актуальной статистики (число строк, кардинальность столбцов, распределение значений) CBO не может правильно оценить, дешевле ли `TABLE ACCESS FULL` или `INDEX RANGE SCAN`, — устаревшая статистика является одной из типичных причин "тяжёлых" запросов.

Частые причины ресурсоёмкого запроса: устаревшая/отсутствующая статистика; проблемы с индексами (не тот индекс, низкая селективность, неактуальная статистика по индексу); неэффективно построенный сам запрос (использование `NOT IN`, функции над индексируемым столбцом блокируют индекс, излишняя вложенность); неверные параметры инициализации БД.

Подсказки оптимизатору (hints) — форсируют конкретный план выполнения:

```sql
SELECT /*+ FULL(emp) */        ename FROM emp;                 -- принудительное полное сканирование
SELECT /*+ INDEX(emp PK_EMP) */ ename FROM emp;                -- принудительное использование индекса
SELECT /*+ USE_NL(emp dept) */ ename, dname FROM emp, dept
WHERE emp.deptno = dept.deptno;                                 -- принудительный nested loop join
SELECT /*+ USE_HASH(emp dept) */ ename, dname FROM emp, dept
WHERE emp.deptno = dept.deptno;                                 -- принудительный hash join
```

Синтаксически важно: пробел после `+` обязателен (`/*+ FULL(emp) */` — верно, `/*+FULL(emp) */` — подсказка будет проигнорирована); если у таблицы есть алиас — в хинте используется алиас, а не исходное имя таблицы.

*Где пригодится: ЛР4 — AC п.4d прямо требует `EXPLAIN`; на защите — типовой вопрос «почему этот запрос выполняется медленно, покажи план».*

```sql
CREATE OR REPLACE VIEW active_employees AS
    SELECT employee_id, last_name, department_id FROM employees WHERE status = 'ACTIVE'
    WITH CHECK OPTION;                        -- запрещает через VIEW вставлять строки, не проходящие условие WHERE

-- материализованное представление — физически хранит результат (для тяжёлых агрегатов)
CREATE MATERIALIZED VIEW dept_salaries
    BUILD IMMEDIATE
    REFRESH FAST ON COMMIT                    -- либо REFRESH COMPLETE / ON DEMAND
```

Простые представления — выборка из одной таблицы; сложные — несколько таблиц, `GROUP BY`/`DISTINCT`, вызовы функций.

*Где пригодится: ЛР4 — AC п.2 буквально называется «получение представлений в БД»; `USER_TAB_COLUMNS`/`USER_CONSTRAINTS` — быстрый способ на защите показать преподавателю структуру своих таблиц без открытия схемы в IDE.*

### Теория

#### Структура блока PL/SQL

```plsql
DECLARE        -- необязательно: константы, переменные, типы, курсоры, исключения
BEGIN          -- обязательно: команды SQL и PL/SQL
EXCEPTION      -- необязательно: обработка ошибок
END;           -- обязательно
```

Минимальный блок: `BEGIN NULL; END;`

Типы блоков: анонимные блоки, процедуры, функции. Среды выполнения — сервер Oracle или клиентская часть (для триггеров — только сервер).

```plsql
DECLARE
  v_name VARCHAR2(100);
BEGIN
  SELECT name INTO v_name FROM salers WHERE id = 106;
  DBMS_OUTPUT.PUT_LINE('Фамилия продавца: ' || v_name);
EXCEPTION
  WHEN OTHERS THEN
    DBMS_OUTPUT.PUT_LINE('Произошла ошибка!');
END;
```

*Где пригодится: ЛР5 — это универсальный «скелет» для тела и процедуры, и функции, и триггера.*

#### Переменные и типы

Скалярные типы: `NUMBER[(p,s)]`, `BINARY_INTEGER`/`PLS_INTEGER` (целые), `CHAR`/`VARCHAR2` (строки), `DATE`/`TIMESTAMP` (даты), `BOOLEAN` (`TRUE`/`FALSE`/`NULL`).

Правила именования переменных: начинаются с буквы, до 30 символов, не зарезервированные слова.

```plsql
DECLARE
  v_start_date DATE;
  v_name       VARCHAR2(100) NOT NULL := 'заглушка';   -- NOT NULL требует немедленной инициализации
  v_sum        NUMBER := 0;
  k_limit      CONSTANT NUMBER := 10000;
```

`%TYPE` — тип переменной берётся из другой переменной/столбца (защищает код от рассинхронизации при изменении типа колонки):

```plsql
v_salary employees.salary%TYPE;
```

`%ROWTYPE` — переменная-запись со структурой, повторяющей строку таблицы или курсора:

```plsql
DECLARE
  emp_rec employees%ROWTYPE;
BEGIN
  SELECT * INTO emp_rec FROM employees WHERE employee_id = 100;
END;
```

*Где пригодится: ЛР5 — `%TYPE`/`%ROWTYPE` в триггерах для работы с `:NEW`/`:OLD` и в процедурах — стандартная практика, экономит правки кода при изменении схемы.*

#### Управляющие конструкции

```plsql
IF condition THEN ... ELSIF condition THEN ... ELSE ... END IF;

LOOP
  ...
  EXIT WHEN condition;
END LOOP;

FOR i IN 1..10 LOOP ... END LOOP;

WHILE condition LOOP ... END LOOP;
```

#### Курсоры

**Неявные** — создаются автоматически для одиночного `SELECT ... INTO`. Атрибуты: `SQL%ROWCOUNT`, `SQL%FOUND`, `SQL%NOTFOUND`, `SQL%ISOPEN` (для неявного курсора всегда `FALSE`, т.к. Oracle закрывает его сразу).

**Явные** — объявляются вручную, когда нужно построчно обработать несколько строк:

```plsql
DECLARE
  CURSOR c_emp IS SELECT employee_id, salary FROM employees WHERE department_id = 10;
  v_id employees.employee_id%TYPE;
  v_sal employees.salary%TYPE;
BEGIN
  OPEN c_emp;
  LOOP
    FETCH c_emp INTO v_id, v_sal;
    EXIT WHEN c_emp%NOTFOUND;
    -- обработка строки
  END LOOP;
  CLOSE c_emp;
END;

-- то же самое компактно, курсорный FOR-цикл сам открывает/закрывает курсор:
BEGIN
  FOR r IN (SELECT employee_id, salary FROM employees WHERE department_id = 10) LOOP
    DBMS_OUTPUT.PUT_LINE(r.employee_id || ' ' || r.salary);
  END LOOP;
END;
```

**Курсорные переменные** (`REF CURSOR`) — доп. гибкость: позволяют передавать указатель на результирующий набор между процедурами/приложением.

*Где пригодится: ЛР5 — явные курсоры нужны в процедурах, которые должны обработать множество строк (например, пересчёт итогов по всем заказам).*

#### Обработка исключений

```plsql
EXCEPTION
  WHEN NO_DATA_FOUND THEN ...
  WHEN TOO_MANY_ROWS  THEN ...
  WHEN OTHERS THEN
    DBMS_OUTPUT.PUT_LINE(SQLCODE || ' ' || SQLERRM);
END;
```

Часто встречающиеся предопределённые исключения (`ORA-NNNNN` — стандартный формат кода ошибки Oracle; `SQLCODE` — числовой код той же ошибки внутри PL/SQL, доступный через функцию `SQLCODE`):

| Исключение | Код ORA / SQLCODE | Когда возникает |
|---|---|---|
| `NO_DATA_FOUND` | ORA-01403 / +100 | `SELECT INTO` не вернул ни одной строки |
| `TOO_MANY_ROWS` | ORA-01422 / -1422 | `SELECT INTO` вернул больше одной строки |
| `DUP_VAL_ON_INDEX` | ORA-00001 / -1 | нарушение `UNIQUE`/`PRIMARY KEY` |
| `INVALID_NUMBER` | ORA-01722 / -1722 | нельзя преобразовать строку в число |
| `ZERO_DIVIDE` | ORA-01476 / -1476 | деление на ноль |
| `CURSOR_ALREADY_OPEN` | ORA-06511 / -6511 | повторное открытие уже открытого курсора |

Пользовательские исключения:

```plsql
DECLARE
  exc_too_young EXCEPTION;
  PRAGMA EXCEPTION_INIT(exc_too_young, -20001);  -- PRAGMA — директива компилятору PL/SQL (не выполняется как код, а задаёт особое поведение); здесь связывает исключение с конкретным кодом ошибки ORA
BEGIN
  IF age < 18 THEN
    RAISE exc_too_young;
    -- либо сразу:
    -- RAISE_APPLICATION_ERROR(-20001, 'Пользователь слишком молод');
  END IF;
EXCEPTION
  WHEN exc_too_young THEN
    DBMS_OUTPUT.PUT_LINE('Ошибка: недопустимый возраст');
END;
```

`RAISE_APPLICATION_ERROR(номер, сообщение)` — номер должен быть в диапазоне -20000..-20999, зарезервированном для пользовательских ошибок приложения.

*Где пригодится: ЛР5 — в триггерах бизнес-валидацию (например, «нельзя удалить последнего администратора») реализуют именно через `RAISE_APPLICATION_ERROR`, это откатывает всю транзакцию.*

#### Хранимые процедуры и функции

Синтаксис (в лекциях детально не раскрыт — восполняется по стандарту Oracle PL/SQL):

```plsql
CREATE OR REPLACE PROCEDURE add_order_item(
    p_order_id IN  NUMBER,
    p_product_id IN NUMBER,
    p_qty IN NUMBER
) AS
BEGIN
    INSERT INTO order_items(order_id, product_id, qty) VALUES (p_order_id, p_product_id, p_qty);
    -- пересчёт суммы заказа — часто выносится в отдельную процедуру/триггер (см. пример ниже)
END add_order_item;
/

CREATE OR REPLACE FUNCTION get_order_total(p_order_id IN NUMBER) RETURN NUMBER AS
    v_total NUMBER := 0;
BEGIN
    SELECT NVL(SUM(qty * price), 0) INTO v_total
    FROM   order_items WHERE order_id = p_order_id;
    RETURN v_total;
END get_order_total;
/

-- вызов:
BEGIN
  add_order_item(1, 42, 3);
END;
/
SELECT get_order_total(1) FROM dual;
```

Параметры процедур: `IN` (по умолчанию, только чтение), `OUT` (только запись, возврат значения вызывающему), `IN OUT` (и чтение, и запись).

*Где пригодится: ЛР5 — прямое требование AC п.2: процедуры должны закрывать часто повторяющиеся операции приложения (добавление в заказ, регистрация пользователя, начисление баллов и т.п.), а не быть искусственными.*

#### Триггеры

**Триггер** — блок PL/SQL, выполняемый неявно при наступлении конкретного события.

Типы событий: DML (`INSERT`/`UPDATE`/`DELETE`), DDL (`CREATE`/`ALTER`/`DROP`), прочие события уровня БД (`LOGON`/`LOGOFF`/`STARTUP`/`SHUTDOWN`/`SERVERERROR`).

```plsql
CREATE [OR REPLACE] TRIGGER имя_триггера
{BEFORE | AFTER | INSTEAD OF} событие [OR событие2 [OR событие3]]
ON {таблица | представление}
[REFERENCING [OLD AS старое] [NEW AS новое]]
[FOR EACH ROW]
[WHEN (условие)]
BEGIN
  тело_триггера;
END;
```

| Параметр | Смысл |
|---|---|
| `BEFORE` | выполняется до операции (удобно для валидации/подмены значений) |
| `AFTER` | выполняется после операции (удобно для аудита, каскадного пересчёта) |
| `INSTEAD OF` | заменяет операцию (только для `VIEW`, которые нельзя изменить напрямую) |
| `FOR EACH ROW` | строчный триггер — срабатывает на каждую затронутую строку (без этого — табличный, один раз на всю команду) |
| `:NEW` / `:OLD` | псевдозаписи с новым/старым значением строки (в `INSERT` есть только `:NEW`, в `DELETE` — только `:OLD`) |

```plsql
-- BEFORE-триггер валидации (проверка бизнес-правила ДО вставки)
CREATE OR REPLACE TRIGGER secure_emp
BEFORE INSERT ON emp
BEGIN
  IF TO_CHAR(SYSDATE,'DY') IN ('SAT','SUN') THEN
    RAISE_APPLICATION_ERROR(-20500, 'Нерабочий день, вставка запрещена');
  END IF;
END;
/

-- AFTER-триггер аудита с :OLD/:NEW
CREATE OR REPLACE TRIGGER history_values
AFTER INSERT OR UPDATE OR DELETE ON tab1
FOR EACH ROW
BEGIN
  INSERT INTO history_tab(user_name, ts, id, old_val, new_val)
  VALUES (USER, SYSDATE, :OLD.id, :OLD.val1, :NEW.val1);
END;
/

-- пример из ЛР5 AC: пересчёт суммы заказа при добавлении товара (реальная бизнес-логика, не просто лог!)
CREATE OR REPLACE TRIGGER trg_recalc_order_total
AFTER INSERT OR UPDATE OR DELETE ON order_items
FOR EACH ROW
DECLARE
  v_order_id order_items.order_id%TYPE;
BEGIN
  v_order_id := NVL(:NEW.order_id, :OLD.order_id);
  UPDATE orders o
  SET    o.total_amount = (SELECT NVL(SUM(qty * price), 0)
                            FROM   order_items WHERE order_id = v_order_id)
  WHERE  o.order_id = v_order_id;
END;
/

-- определение конкретного вида DML-события внутри одного триггера
CREATE OR REPLACE TRIGGER t
BEFORE INSERT OR UPDATE OF salary, department_id OR DELETE ON employees
BEGIN
  CASE
    WHEN INSERTING THEN DBMS_OUTPUT.PUT_LINE('Inserting');
    WHEN UPDATING('salary') THEN DBMS_OUTPUT.PUT_LINE('Updating salary');
    WHEN DELETING THEN DBMS_OUTPUT.PUT_LINE('Deleting');
  END CASE;
END;
/

-- WHEN — условие срабатывания строчного триггера (проверяется для каждой строки до входа в тело)
CREATE OR REPLACE TRIGGER derive_commission_pct
BEFORE INSERT OR UPDATE OF sal ON emp
FOR EACH ROW
WHEN (NEW.job = 'SALESMAN')
BEGIN
  :NEW.comm := :NEW.sal * 0.1;
END;
/

-- INSTEAD OF — единственный способ сделать VIEW из нескольких таблиц "обновляемым"
CREATE OR REPLACE TRIGGER tr_instead
INSTEAD OF UPDATE ON v_view1
FOR EACH ROW
BEGIN
  UPDATE base_table SET col = :NEW.col WHERE id = :NEW.id;
END;
/
```

Порядок выполнения триггеров при одной DML-команде: `BEFORE (табличный) → BEFORE FOR EACH ROW → операция со строкой → AFTER FOR EACH ROW → проверка ограничений → AFTER (табличный)`. Порядок нескольких одноуровневых триггеров можно зафиксировать через `FOLLOWS имя_триггера`.

**COMPOUND TRIGGER** — один триггер с четырьмя секциями (`BEFORE STATEMENT` / `BEFORE EACH ROW` / `AFTER EACH ROW` / `AFTER STATEMENT`), удобен, когда нужно накопить состояние по всем строкам операции и что-то сделать один раз после неё (обходит проблему мутирующих таблиц, см. ниже).

```plsql
CREATE OR REPLACE TRIGGER tr_compound
FOR UPDATE OR DELETE OR INSERT ON tab1
COMPOUND TRIGGER
  v_count NUMBER := 0;
  BEFORE STATEMENT IS BEGIN v_count := 0; END BEFORE STATEMENT;
  AFTER EACH ROW IS BEGIN v_count := v_count + 1; END AFTER EACH ROW;
  AFTER STATEMENT IS BEGIN DBMS_OUTPUT.PUT_LINE('Изменено строк: '||v_count); END AFTER STATEMENT;
END tr_compound;
```

**Автономные транзакции** — триггер может зафиксировать (`COMMIT`) свою логику независимо от основной транзакции (например, для логирования, которое должно сохраниться даже при откате основной операции):

```plsql
CREATE OR REPLACE TRIGGER emp_trigger
BEFORE UPDATE OF sal ON emp
FOR EACH ROW
PRAGMA AUTONOMOUS_TRANSACTION;
BEGIN
  IF :NEW.sal > :OLD.sal * 1.3 THEN
    INSERT INTO emp_audit(person, dt) VALUES (USER, SYSDATE);
    COMMIT;                                  -- фиксация именно этой автономной транзакции
    RAISE_APPLICATION_ERROR(-20001, 'Слишком большое повышение зарплаты');
  END IF;
END;
```

**Мутирующая таблица (mutating table error, ORA-04091)** — типичная ошибка: строчный триггер пытается прочитать/изменить ту же таблицу, на которой он определён (в момент срабатывания она ещё «в процессе изменения» и недоступна для непротиворечивого чтения). Решения: перенести агрегирующую логику в `AFTER STATEMENT` часть `COMPOUND TRIGGER`, либо использовать вспомогательную PL/SQL-таблицу/пакетную переменную для накопления изменений построчно и обработки их одним запросом в конце.

*Где пригодится: ЛР5 — это ядро всей лабы. AC явно требует, чтобы триггеры реализовывали **автоматизированную бизнес-логику** (пересчёт суммы заказа, каскадное обновление, проверка бизнес-правил), а не только аудит/логирование — это отдельно прописано как критерий, по которому лаба НЕ засчитывается.*

#### Пакеты (удобная организация процедур для ЛР5)

Пакет = спецификация (интерфейс) + тело (реализация). Позволяет логически сгруппировать связанные процедуры/функции проекта (например, весь функционал по заказам).

```plsql
CREATE OR REPLACE PACKAGE orders_pkg IS
  PROCEDURE add_item(p_order_id NUMBER, p_product_id NUMBER, p_qty NUMBER);
  FUNCTION  get_total(p_order_id NUMBER) RETURN NUMBER;
END orders_pkg;
/
CREATE OR REPLACE PACKAGE BODY orders_pkg IS
  PROCEDURE add_item(p_order_id NUMBER, p_product_id NUMBER, p_qty NUMBER) IS
  BEGIN
    INSERT INTO order_items(order_id, product_id, qty) VALUES (p_order_id, p_product_id, p_qty);
  END;
  FUNCTION get_total(p_order_id NUMBER) RETURN NUMBER IS
    v_total NUMBER;
  BEGIN
    SELECT NVL(SUM(qty*price),0) INTO v_total FROM order_items WHERE order_id = p_order_id;
    RETURN v_total;
  END;
END orders_pkg;
/
-- вызов: orders_pkg.add_item(1, 42, 3);
```

Преимущества пакетов: модульность, простота проектирования, сокрытие приватной реализации (в спецификацию выносится только публичный интерфейс), пакетные переменные (состояние на сессию), возможность перегрузки одноимённых процедур с разными сигнатурами параметров.

*Где пригодится: ЛР5 — необязательно по AC, но на защите выглядит аккуратнее, чем десяток разрозненных процедур; удобно, когда процедур становится много.*

#### Коллекции (для более сложных процедур)

Если процедуре нужно вернуть/обработать не одну строку, а набор значений — используются коллекции:

| Вид коллекции | Особенность |
|---|---|
| Ассоциативный массив (`INDEX BY`) | пары ключ-значение, не хранится в таблицах БД, только в памяти PL/SQL |
| Вложенная таблица (`TABLE OF`) | размер меняется динамически, может храниться как тип столбца таблицы |
| VARRAY | фиксированный максимальный размер, последовательный доступ |

```plsql
DECLARE
  TYPE t_ids IS TABLE OF NUMBER INDEX BY PLS_INTEGER;
  v_ids t_ids;
BEGIN
  v_ids(1) := 10; v_ids(2) := 20;
  FOR i IN v_ids.FIRST .. v_ids.LAST LOOP
    DBMS_OUTPUT.PUT_LINE(v_ids(i));
  END LOOP;
END;
```

Методы коллекций: `COUNT`, `EXISTS(n)`, `FIRST`/`LAST`, `NEXT(n)`/`PRIOR(n)`, `EXTEND`, `TRIM`, `DELETE`.

*Где пригодится: ЛР5 (опционально) — если процедура должна массово обработать список ID, переданный из приложения.*

## Лабораторная работа №6 — Приложение с UI поверх БД

### Условие
1. Создать приложение с пользовательским интерфейсом, в котором разработанная за семестр БД выступает основной БД проекта.

### Acceptance Criteria
1. Приложение имеет интерфейс взаимодействия с пользователем:
   - a. Консольное — реализован список команд для взаимодействия.
   - b. Веб/десктоп — реализован условный frontend.
2. Приложение соответствует ТЗ, утверждённому в ЛР1.
3. В качестве БД используется база, спроектированная в ЛР1-5, подключённая **напрямую**.
4. Взаимодействие с БД — одним из трёх способов:
   - a. Прямые запросы в БД из приложения.
   - b. Самописная ORM (ORM — Object-Relational Mapping, технология сопоставления объектов языка программирования строкам/таблицам БД; демонстрация **своего** исходного кода ORM обязательна).
   - c. `ORM.raw_sql()` или аналог в используемых технологиях.

   **Взаимодействие с БД должно осуществляться исключительно при помощи SQL** — иначе лаба не засчитывается.
5. Для взаимодействия используются запросы, разработанные в ЛР3-5.
6. Способность добавить детали в код проекта непосредственно при сдаче.
7. Теоретические знания в контексте лабораторной.

### Теория

В лекциях курса отдельной темы про архитектуру приложений нет — эта ЛР проверяет умение соединить уже готовую БД (ЛР1-5) с кодом. Ниже — минимально необходимая теория для закрытия AC.

#### Три допустимых способа работы с БД из приложения

1. **Прямые SQL-запросы.** Приложение открывает соединение (JDBC/ODBC — стандартные программные интерфейсы для подключения приложения к БД, соответственно для Java и для языков в целом через универсальный драйвер; psycopg2/cx_Oracle/oracledb — конкретные библиотеки-драйверы для Python и т.п.) и выполняет `SELECT`/`INSERT`/`UPDATE`/`DELETE`/вызовы хранимых процедур из ЛР3-5 напрямую, без прослойки ORM.

   ```python
   import oracledb
   conn = oracledb.connect(user="app", password="...", dsn="localhost/orclpdb")
   cur = conn.cursor()
   cur.execute("SELECT order_id, total_amount FROM orders WHERE customer_id = :id", id=42)
   for row in cur:
       print(row)
   cur.callproc("orders_pkg.add_item", [1, 42, 3])   -- вызов хранимой процедуры из ЛР5
   conn.commit()
   ```

2. **Самописная ORM.** Минимальный смысл ORM — отображение строки таблицы на объект языка программирования и обратно (мэппинг). Даже упрощённая реализация должна: (а) хранить соответствие класс↔таблица и поле↔колонка; (б) уметь построить `SELECT`/`INSERT`/`UPDATE`/`DELETE` по объекту; (в) исполнять их через параметризованные запросы (см. ниже про SQL-инъекции). Демонстрация исходного кода такой ORM — обязательное требование AC 4b.

3. **`ORM.raw_sql()` / аналог.** Использование готовой ORM (SQLAlchemy, Django ORM, Hibernate и т.п.), но с явным вызовом «сырого» SQL (например, `session.execute(text("SELECT ..."))`), а не автогенерируемых ORM-запросов — требование в том, чтобы именно ваши SQL-запросы из ЛР3-5 управляли обращением к БД, а не автоматика ORM.

*Где пригодится: ЛР6 — AC прямым текстом требует, чтобы работа шла **исключительно** через SQL; любой из трёх способов допустим, но использование «чистого» ORM без raw SQL (когда ORM сама генерирует запросы без вашего участия) не защитывается.*

#### Обязательные практические моменты

- **Параметризованные запросы (bind variables)** вместо конкатенации строк — обязательно для защиты от SQL-инъекций:
  ```sql
  -- плохо:  "SELECT * FROM users WHERE login = '" + input + "'"
  -- хорошо: SELECT * FROM users WHERE login = :login   -- значение передаётся отдельно от текста запроса
  ```
- **Транзакции на уровне приложения**: операция, состоящая из нескольких SQL-команд (например, оформление заказа = вставка в `orders` + вставка в `order_items`), должна быть одной транзакцией — `commit()` только после успешного выполнения всех шагов, иначе `rollback()`.
- **Слой доступа к данным (Repository/DAO — Data Access Object, «объект доступа к данным»: отдельный класс/модуль, инкапсулирующий весь SQL к конкретной таблице/сущности)**: даже в консольном приложении стоит выносить весь SQL в отдельный модуль/класс, а не размешивать его по всему UI-коду (UI — User Interface, пользовательский интерфейс) — это упрощает демонстрацию «пула запросов из ЛР3-5» на защите.
- Приложение должно закрывать функциональные требования ЛР1 (авторизация, CRUD пользователей, роли, журналирование действий) — это то же самое ТЗ, не новое.

# Дополнительно: за пределами обязательных лабораторных, но пригодится в реальной работе с БД

## 1. Другие модели данных: NoSQL СУБД (обзор)

Материал не привязан ни к одной ЛР (все лабораторные курса используют реляционную СУБД), но входит в лекционный курс как общая эрудиция и часто спрашивается на защите/экзамене как «а чем отличается…».

Причина появления NoSQL: строгие ACID-свойства реляционных БД ограничивают горизонтальное масштабирование под очень высокую нагрузку.

Классификация NoSQL:

| Тип хранилища | Модель данных | Пример |
|---|---|---|
| Ключ-значение | ассоциативный массив/словарь, максимальная производительность | Redis |
| Документ-ориентированное | вложенные документы (JSON/BSON), собираются в коллекции без жёсткой схемы | MongoDB |
| Колоночное | кортежи `<ключ строки, ключ столбца, timestamp>`, колонки объединяются в семейства | Cassandra, HBase |
| Графовое | вершины, рёбра, свойства; обход графа по рёбрам | Neo4j |

**Redis** (key-value): типы данных — строки, списки, множества, хеш-таблицы, упорядоченные множества.
```
SET key value        GET key
MSET k1 v1 k2 v2      MGET k1 k2
HMSET user:1 name "Adam" password "x"     HGET user:1 password
RPUSH list1 "a" "b"   LRANGE list1 0 -1
SADD set1 "a" "b"     SMEMBERS set1
```
Транзакции — через `MULTI`/`EXEC`/`DISCARD`.

**MongoDB** (документ-ориентированное): единица хранения — документ, набор документов — коллекция, доступ `база.коллекция.функция`.
```js
db.students.insert({first_name:"Иван", birthday: ISODate("2000-01-01"),
                     certificates:["SAP","ASP.Net"]})
db.students.find({last_name: /^И/, birthday: {$lt: ISODate("2001-01-01")}})
db.students.update({"_id": id}, {$set: {sex: "male"}})
db.students.remove({"_id": id})
```
Булевы операторы запроса: `$or`, `$lt`, `$gt`, `$lte`, `$regex`, `$exists`, `$all`, `$in`, `$nin`, `$elemMatch`. Модификаторы обновления: `$set`, `$unset`, `$inc`, `$push`, `$pull`, `$addToSet`.

**Neo4j** (графовое): собственный язык запросов Cypher, также используется язык Gremlin.
```
g.V().filter(it.LastName == 'John')          // поиск вершины
g.V().filter(it.LastName == 'John').outE()   // исходящие рёбра
g.addVertex([...])                            // создать вершину
g.addEdge(node1, node2, type)                 // создать ребро
```

*Где пригодится: общая эрудиция/собеседования — реляционная модель (курс) хороша для строгой целостности и сложных связей, NoSQL — для горизонтального масштабирования и гибкой схемы.*

## 2. Продвинутый PL/SQL: пакеты, объектные типы, очереди, взаимодействие сеансов

Материал не требуется ни одним AC, но напрямую продолжает тему ЛР5 и встречается в реальных Oracle-проектах.

### Перегрузка процедур в пакете

Одно имя, разные сигнатуры параметров (отличаются количеством/порядком/семейством типов, но не только именами или только режимом параметра, и не только типом возврата):

```plsql
PROCEDURE initialize(tab OUT datetab_t, n INTEGER) IS ...
PROCEDURE initialize(tab OUT realtab_t, n INTEGER) IS ...
```

### Готовые пакеты Oracle

| Пакет | Назначение |
|---|---|
| `DBMS_OUTPUT` | вывод сообщений из PL/SQL (отладка) |
| `DBMS_SQL` | динамический SQL |
| `DBMS_JOB` / `DBMS_SCHEDULER` | планирование периодического выполнения кода |
| `DBMS_ALERT` | уведомления о событиях БД между сеансами (транзакционные) |
| `DBMS_PIPE` | двунаправленный канал сообщений между сеансами (нетранзакционный) |
| `DBMS_LOCK` | пользовательские блокировки |
| `UTL_FILE` | файловый ввод-вывод из PL/SQL |
| `UTL_SMTP` / `UTL_HTTP` | отправка почты / HTTP-запросы из БД |

### Объектные типы Oracle (ООП в PL/SQL)

```plsql
CREATE OR REPLACE TYPE discount_price_obj AS OBJECT (
  discount_rate NUMBER(10,4),
  price         NUMBER(10,2),
  MEMBER FUNCTION discount_price RETURN NUMBER
) INSTANTIABLE FINAL;
/
CREATE OR REPLACE TYPE BODY discount_price_obj AS
  MEMBER FUNCTION discount_price RETURN NUMBER IS
  BEGIN
    RETURN SELF.price * (1 - SELF.discount_rate);
  END;
END;
/
DECLARE
  v_price discount_price_obj := discount_price_obj(.1, 75.00);
BEGIN
  DBMS_OUTPUT.PUT_LINE(v_price.discount_price);
END;
```

Ключевые возможности: конструктор (`CONSTRUCTOR FUNCTION ... RETURN SELF AS RESULT`), методы экземпляра (`MEMBER`) и статические (`STATIC`), наследование (`CREATE TYPE child UNDER parent (...)`), переопределение методов (`OVERRIDING MEMBER`), сравнение объектов (`MAP MEMBER FUNCTION` — через промежуточное скалярное значение; `ORDER MEMBER FUNCTION` — через явное попарное сравнение), приведение типов (`TREAT`), объектные таблицы (`CREATE TABLE t OF object_type`), объектные представления (`CREATE VIEW v OF object_type WITH OBJECT IDENTIFIER (...)`). Ограничения ООП в PL/SQL: нет модификаторов видимости (все члены `PUBLIC`), нет свойств (property), нет статических атрибутов типа (эмулируются через пакет).

### Oracle Advanced Queuing (AQ) — очереди сообщений

```plsql
BEGIN
  DBMS_AQADM.CREATE_QUEUE_TABLE(queue_table => 'msg_qt', queue_payload_type => 'msg_type');
  DBMS_AQADM.CREATE_QUEUE(queue_name => 'queue1', queue_table => 'msg_qt');
  DBMS_AQADM.START_QUEUE(queue_name => 'queue1');
END;
/
-- отправка сообщения
DECLARE
  enq_opt DBMS_AQ.enqueue_options_t;
  msg_prop DBMS_AQ.message_properties_t;
  msg_id RAW(16);
  msg msg_type := msg_type(1, 'Subject', 'Text');
BEGIN
  DBMS_AQ.ENQUEUE(queue_name => 'queue1', enqueue_options => enq_opt,
                   message_properties => msg_prop, payload => msg, msgid => msg_id);
  COMMIT;
END;
```

### Взаимодействие между сеансами

- `DBMS_ALERT` — транзакционные однонаправленные широковещательные сигналы (`REGISTER`/`WAITONE`/`SIGNAL`).
- `DBMS_PIPE` — внетранзакционный двунаправленный канал (`PACK_MESSAGE`/`SEND_MESSAGE`/`UNPACK_MESSAGE`/`RECEIVE_MESSAGE`), каналы неявные (авто) и явные (`CREATE_PIPE`), публичные и приватные.
- `DBMS_LOCK` — пользовательские блокировки поверх стандартных механизмов Oracle (`ALLOCATE_UNIQUE` → `REQUEST` → `RELEASE`), режимы `NL/SS/SX/S/SSX/X` по нарастанию строгости.
- Контекст сеанса (`CREATE CONTEXT`, `SYS_CONTEXT`) и **VPD/Row-Level Security** (VPD — Virtual Private Database, «виртуальная частная база данных»; `DBMS_RLS.ADD_POLICY`) — построчный контроль доступа к данным на уровне БД, без изменения текста запросов приложения.
- `DBMS_SCHEDULER` — более гибкая замена `DBMS_JOB` для периодических заданий (`CREATE_JOB`, `repeat_interval => 'FREQ=DAILY; INTERVAL=1'`).

*Где пригодится: в реальных enterprise Oracle-проектах — интеграция между модулями системы без брокера сообщений (AQ/DBMS_PIPE), многоарендная (multi-tenant) безопасность на уровне строк (RLS), фоновые задачи (Scheduler).*

## 3. Администрирование Oracle

Материал не привязан ни к одной из 6 лабораторных (это отдельная дисциплина — эксплуатация промышленной БД), но необходим для реальной работы с Oracle в проде.

### Архитектура экземпляра и файлы

- **OFA (Optimal Flexible Architecture)** — стандарт размещения ПО и файлов Oracle для упрощения администрирования.
- Переменные среды: `ORACLE_BASE`, `ORACLE_HOME`, `ORACLE_SID`, `NLS_LANG`, `ORACLE_UNIQNAME`.
- **Управляющие файлы (control files)** — физическая структура БД, рекомендуется мультиплексировать (≥2 копии на разных дисках). `SELECT name FROM v$controlfile;`
- **Оперативные журналы (online redo logs)** — журналы повторного выполнения: хранят все изменения данных для возможности восстановления после сбоя; обрабатываются процессом LGWR (Log Writer — фоновый процесс, записывающий буфер журнала на диск), требуют мультиплексирования внутри группы. `SELECT group#, member FROM v$logfile ORDER BY group#;`
- **Файлы параметров**: `spfile` (бинарный, используется при старте) и `pfile` (текстовый, запасной вариант).
- **Табличные пространства (tablespaces)** состоят из файлов данных; внутри — сегменты → экстенты → блоки данных.
- Методы разрешения имён Oracle Net (сетевой протокол Oracle, ранее известный как TNS — Transparent Network Substrate; на нём основано имя файла `tnsnames.ora`): упрощённое соединение (`connect hr/hr@host:port/service`), локальное именование (файл `tnsnames.ora`), каталог имён (LDAP — Lightweight Directory Access Protocol, протокол доступа к централизованному каталогу-справочнику), внешнее именование. Проверка — `tnsping`, управление слушателем (listener — сетевая служба Oracle, принимающая входящие подключения к БД) — `lsnrctl start/stop/status`.

### Управление информацией отмены (UNDO)

Информация отмены — копия исходных данных до модификации; хранится в сегментах отмены табличного пространства UNDO; используется для операций отката, для целостного по чтению доступа (снимки данных на момент старта запроса) и восстановления аварийно прерванных транзакций.

```sql
CREATE UNDO TABLESPACE undotbs_02 DATAFILE '...' SIZE 500M;
ALTER SYSTEM SET UNDO_TABLESPACE = undotbs_02;
ALTER SYSTEM SET UNDO_RETENTION = 3600;              -- сколько секунд хранить отменённые данные
ALTER TABLESPACE undotbs01 RETENTION GUARANTEE;       -- гарантировать хранение (риск переполнения UNDO)
```
Мониторинг: свободное место в UNDO tablespace, ошибки «snapshot too old» (не хватило истории для целостного чтения долгого запроса).

### Резервное копирование и восстановление

Классификация backup: по объекту (логический — схемы/таблицы через `exp`/`expdp`, физический — файлы/блоки), по состоянию БД («холодный» — БД закрыта, «горячий» — БД открыта), по объёму («полный», «инкрементальный» — только изменившиеся блоки: дифференциальный копирует изменения с последнего backup любого уровня, кумулятивный — с последнего backup уровня 0).

Инструменты: `exp`/`imp` (устаревшие), **Data Pump** (`expdp`/`impdp` — параллелизм, оценка объёма, сетевой режим), **RMAN** (Recovery Manager) — основной современный инструмент.

```
rman target /
RMAN> BACKUP DATABASE PLUS ARCHIVELOG;
RMAN> CONFIGURE CONTROLFILE AUTOBACKUP ON;
RMAN> BACKUP INCREMENTAL LEVEL 0 DATABASE;   -- база для дифференциального инкремента
RMAN> BACKUP INCREMENTAL LEVEL 1 DATABASE;   -- только изменения с уровня 0
RMAN> LIST BACKUP;
RMAN> CROSSCHECK BACKUP;
RMAN> DELETE NOPROMPT OBSOLETE;
-- восстановление:
RMAN> RESTORE CONTROLFILE FROM '<backup>';
RMAN> ALTER DATABASE MOUNT;
RMAN> RESTORE DATABASE;
RMAN> RECOVER DATABASE;
RMAN> ALTER DATABASE OPEN RESETLOGS;
```

Режим `ARCHIVELOG` необходим для полного (а не только на момент последнего backup) восстановления:
```sql
SHUTDOWN IMMEDIATE; STARTUP MOUNT; ALTER DATABASE ARCHIVELOG; ALTER DATABASE OPEN;
```

**Flashback**-технологии (без полного восстановления из backup):
```sql
SELECT * FROM employees AS OF TIMESTAMP TO_TIMESTAMP('2017-03-22 08:00:00','YYYY-MM-DD HH24:MI:SS');
FLASHBACK TABLE emp TO SCN 1234567890;   -- SCN (System Change Number) — внутренний монотонно растущий номер версии данных Oracle, используется вместо/вместе со временем для точной идентификации момента
DROP TABLE tab1;
FLASHBACK TABLE tab1 TO BEFORE DROP;              -- восстановление из "корзины"
FLASHBACK DATABASE TO TIMESTAMP TO_TIMESTAMP('...');
```

### Масштабирование и репликация

| Тип | Технология |
|---|---|
| Горизонтальное (репликация) | Oracle Streams, GoldenGate, Active Data Guard |
| Вертикальное (кластер) | Real Application Cluster (RAC) |

Streams: процессы **Capture** (чтение журналов транзакций → LCR, Logical Change Record — «логическая запись об изменении», внутреннее представление одного изменения строки), **Propagation** (передача LCR между очередями), **Apply** (применение изменений). Репликация бывает синхронной (2PC — Two-Phase Commit, «двухфазная фиксация»: протокол, гарантирующий, что транзакция либо зафиксируется одновременно на всех узлах, либо не зафиксируется нигде; без конфликтов, требует постоянной связи) и асинхронной (Store & Forward, возможны конфликты, не зависит от связи). Разрешение конфликтов: последний/первый по времени, приоритет группы/сайта, суммирование, среднее, максимум/минимум.

RAC — несколько экземпляров БД на разных узлах кластера работают с одной общей БД (общее хранилище), обеспечивая горизонтальное масштабирование и высокую доступность.

### Оптимизация и мониторинг производительности

Выбор пути доступа (полное сканирование / доступ по ROWID / сканирование индекса) и метода соединения (nested loop / hash join / sort-merge join) — задача CBO (см. также раздел EXPLAIN в ЛР4). Статистика собирается через `DBMS_STATS` (по схеме/таблице/БД/системе).

**SQL Tuning Advisor** — автоматический советчик по конкретному запросу:
```plsql
DECLARE
  v_task VARCHAR2(30);
BEGIN
  v_task := DBMS_SQLTUNE.CREATE_TUNING_TASK(sql_text => '...', task_name => 'my_task');
  DBMS_SQLTUNE.EXECUTE_TUNING_TASK(task_name => 'my_task');
END;
/
SELECT DBMS_SQLTUNE.REPORT_TUNING_TASK('my_task') FROM DUAL;
```

**Result Cache** — кэш результатов запроса на стороне сервера (`RESULT_CACHE_MODE=FORCE` или хинт `/*+ RESULT_CACHE */`), не работает для представлений, удалённых объектов, PL/SQL-функций в запросе, Flashback-запросов.

Мониторинг: **AWR** (Automatic Workload Repository) — снимки метрик каждые ~60 минут, хранение по умолчанию 7 дней, база для всех автоматических советчиков; **ADDM** (Automatic Database Diagnostic Monitor) — автоматически анализирует каждый снимок AWR и находит узкие места. Представления `V$SYSMETRIC`, `V$SYSMETRIC_HISTORY`, `DBA_HIST_*`. Советчики (advisors): SQL Tuning, использования памяти (Shared Pool/Buffer Cache — области разделяемой памяти сервера, входящие в SGA, System Global Area; PGA — Program Global Area, область памяти, выделяемая отдельно под каждый серверный процесс/сеанс), сегментный, undo.

### RMAN, флешбек и Data Pump — детали параметров

```
expdp scott/tiger schemas=SCOTT directory=TEST_DIR dumpfile=SCOTT.dmp logfile=expdpSCOTT.log
expdp scott/tiger schemas=SCOTT include=TABLE:"IN ('EMP','DEPT')" directory=TEST_DIR dumpfile=SCOTT.dmp
```
Режимы Data Pump Export: `FULL` (вся БД), `SCHEMAS`, `TABLESPACES`/`TRANSPORT_TABLESPACES`, `TABLES`.

### Oracle ASM (Automatic Storage Management)

Кластерная файловая система для файлов БД: автоматическое распределение/балансировка данных между дисками «на лету», встроенное зеркалирование. ASM-инстанс (`INSTANCE_TYPE=ASM`) отдельно от инстанса БД, управляет дисковыми группами (Disk Group), которые состоят из ASM-дисков, разбитых на allocation units (по умолчанию 1 МБ). Виды избыточности дисковой группы: `EXTERNAL REDUNDANCY` (без зеркалирования, полагается на внешний RAID — Redundant Array of Independent Disks, аппаратный/программный массив дисков с собственной избыточностью), `NORMAL REDUNDANCY` (двойное зеркалирование), `HIGH REDUNDANCY` (тройное).

```sql
CREATE DISKGROUP data1 EXTERNAL REDUNDANCY DISK '/dev/raw/raw1';
ALTER DISKGROUP data1 ADD DISK '/dev/raw/raw4';
CREATE TABLESPACE sample DATAFILE '+DATA1';
```
